## 1. Как выбирается вторая модель

В Code-ноде `Settings` заданы два разных ID:

```js
primaryModel: 'openai/gpt-5.2',
secondaryModel: 'openai/gpt-6-sol',
```

`GitHub Events` принимает события `pull_request` и `issue_comment`. `Normalize Event` пропускает открытие PR (`action=opened`) и новые комментарии (`action=created`) с точными командами после удаления пробелов по краям. Комментарии в обычных Issues, прочий текст и боты отфильтровываются. Команды разрешены логину DaniilEF через `allowedLogins`.

| Событие | review_kind | Модель и ветка |
|---|---|---|
| Открытие PR | opened | gpt-5.2 → Primary Review Agent |
| `/make_ai_review` | make_ai_review | gpt-5.2 → Primary Review Agent |
| `/make_other_ai_review` | make_other_ai_review | gpt-6-sol → Secondary Review Agent |

После проверки дедупликации нода `Use Secondary Model?` выбирает ветку по полю `secondary`. У каждой ветки свой Agent и Chat Model; ID модели берётся выражением из Settings. Результат публикуется в том же PR, в заголовке указаны модель и review_kind.

**Наблюдаемое различие результатов:** на показанном прогоне gpt-5.2 предложила изменить проверку равенства массивов в тесте; gpt-6-sol обратила внимание на граничный случай регулярного выражения — 40 символов и завершающий перевод строки. Это различия конкретных ответов, а не доказательство общего превосходства одной модели.

Опубликованные замечания требуют проверки разработчиком. Например, исходный контракт явно требует возвращать исходный массив при пустой строке, поэтому замечание о сравнении ссылок нужно оценивать с учётом этого контракта.

## 2. Где хранится состояние

Используется встроенная n8n Data Table `pr_reviews_inline`. Для первого, базового варианта создана отдельная таблица; данные двух вариантов не смешиваются.

| Поле | Тип | Назначение |
|---|---|---|
| repo_full_name | String | Полное имя GitHub-репозитория |
| pr_number | Number | Номер PR внутри репозитория |
| pr_id | Number | Глобальный ID PR GitHub |
| review_kind | String | opened / make_ai_review / make_other_ai_review |
| model | String | ID использованной модели |
| comment_url | String | Ссылка на опубликованный результат |
| head_sha | String | SHA проверенного коммита |

Системный `id` строки n8n не является ID PR. В показанной таблице PR №3 имеет `pr_id=5344190281`; для него сохранены две строки с моделями gpt-5.2 и gpt-6-sol.

`Find Reviewed PR` читает строки по repo_full_name и pr_number с условием All Conditions. Включены Return All и Always Output Data: при пустом результате проверка продолжается и разрешает первый запуск.

Запись создаётся в конце цепочки: `Publish Review → Prepare Success Row → Save Reviewed PR`. Если LLM или публикация завершились ошибкой, успешная строка не создаётся.

## 3. Что происходит при повторном /make_ai_review

`Dedup Check` проверяет строки таблицы до получения diff и обращения к модели:

- Основная команда и автоматическое открытие блокируются любой успешной записью для пары repo_full_name + pr_number.
- Вторая команда разрешена после основной модели, но блокируется, если для этого PR уже есть запись make_other_ai_review.
- head_sha хранится для аудита и не сбрасывает дедупликацию: добавление коммитов не разрешает повтор основной команды к уже проверенному PR.

При повторной основной команде выставляется `already_reviewed=true`; нода `Already Reviewed?` отправляет выполнение в `Skip Duplicate`. Agent, публикация и вставка новой строки не выполняются. Новый комментарий-команда создаёт Execution, но повторное ревью внутри него не запускается.

Подтверждение: [Execution с веткой Skip Duplicate](<HW_7.1_proves/07-dedup-skip-execution.png>). На скриншоте видна блокировка; вход с текстом команды и номером PR нужно открыть в этом Execution при демонстрации.

Публикация результата также создаёт GitHub-событие комментария. Такой запуск может появиться отдельно в Executions, но завершается в Normalize Event: текст review не совпадает с командой. Это фильтрация события, а не ветка дедупликации.

## 4. Как реализованы точечные комментарии

В inline-workflow в Settings задано `mode: 'inline'`.

1. `Get PR Metadata` и `Capture PR` получают ID, номер и head SHA PR.
2. `Get PR Diff` получает текст unified diff через GitHub API с заголовком Accept: application/vnd.github.diff.
3. `Prepare Review` разбирает diff на файлы и хунки. Каждый хунк становится блоком с block_id, path, заголовком, текстом и изменёнными строками.
4. Счётчики старых и новых номеров строк ведутся отдельно. Добавленные строки получают сторону RIGHT и новый номер, удалённые — LEFT и старый номер. Контекст увеличивает оба счётчика. Блоки только с удалениями также учитываются.
5. Все блоки передаются выбранной модели одним запросом. Модель должна вернуть JSON с отдельным результатом для каждого block_id: assessment и массив comments. Отдельный запрос на каждый блок не используется.
6. `Build Publication` требует ровно один результат на каждый блок и проверяет каждый комментарий по тройке path + side + line. Комментарий разрешён только на изменённой строке соответствующего блока. Дубли одной привязки удаляются.
7. Если замечаний к блоку нет, на первой изменённой строке публикуется assessment, полученный от модели. Пропущенный блок, невалидный JSON или неверная привязка вызывают ошибку до публикации.
8. `Publish Review` отправляет `POST /repos/{owner}/{repo}/pulls/{number}/reviews` с event=COMMENT, сохранённым commit_id и массивом comments. GitHub показывает комментарии у строк diff, а не только общим сообщением в Conversation.

SHA проверяется после получения diff и перед публикацией. Если PR изменился или закрылся во время обработки, публикация останавливается.

Подтверждения: [комментарии к app.js и тестам](<HW_7.1_proves/02-secondary-inline-code-comments.png>), [другие блоки](<HW_7.1_proves/04-primary-inline-test-comments.png>), [успешная полная цепочка основной модели](<HW_7.1_proves/06-primary-review-execution.png>). Покрытие всех блоков проверяется по полному PR и выходу blocks ноды Prepare Review; несколько скриншотов демонстрируют примеры привязки, а не весь diff.

## 5. Как повторить демонстрацию

1. Импортировать рабочий экспорт inline-workflow, выбрать GitHub и учебные LLM credentials, указать реальные разные model ID.
2. Создать Data Table с указанными колонками и выбрать одну и ту же таблицу в обеих Data Table нодах. Активировать только один вариант workflow.
3. В PR без записи второй модели отправить новым комментарием `/make_other_ai_review`. Показать Execution второй ветки и опубликованный review.
4. Открыть Data Table и показать запись с ID этого PR и ссылкой на результат.
5. Отправить новым комментарием `/make_ai_review`. Показать вход события, ветку Skip Duplicate и отсутствие вызова Agent.
6. Открыть комментарии review в GitHub и сопоставить их с блоками diff и номерами строк.

На текущем PR №3 обе модели уже записаны в таблицу: повтор второй команды тоже блокируется. Для нового полного прогона использовать другой PR с кодом и новой записью состояния. Существующие доказательства удалять не требуется.

## 6. Ограничения

- Учебные пределы: diff до 60 000 символов, до 20 блоков и до 30 inline-комментариев. При превышении сценарий завершается ошибкой, не обрезая результат молча.
- Бинарные diff и quoted/escaped пути не поддержаны и отклоняются явно. Изменения без текстовых хунков не получают линейных комментариев.
- Проверка Get → Insert не является атомарной блокировкой: одновременные события могут привести к дублю. Демонстрационные запуски выполнялись последовательно.
- Если публикация прошла, а сохранение строки упало, перед повтором всей цепочки нужно восстановить состояние таблицы, иначе возможно повторное review.
- Экспорт workflow не включает Data Table и историю Executions; их содержимое подтверждается отдельно.
- Оценка выставляется ревьювером по реальным запускам и полноте материалов, а не по одному наличию нод или JSON.
