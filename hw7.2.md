## 1. Классификация Issues и выбор ветки

`New GitHub Issue` получает события `issues`. `Normalize Issue` принимает только `action=opened` в выбранном репозитории и исключает PR. Основной workflow вызывает `Call Issue Classifier`, передавая строки `title` и `body`, и ждёт результат.

В классификаторе: `Classifier Input → Prepare Classifier Input → Classify Issue → Return Classification`. Basic LLM Chain подключена к Chat Model и Structured Output Parser. Классификатор возвращает `type` и числовой `confidence` от 0 до 1.

- bug — ошибка текущего поведения;
- task — конкретная техническая задача;
- feature — новая возможность;
- unknown — тип нельзя определить уверенно.

`Validate and Route` проверяет ответ, `Switch Issue Type` выбирает одну из веток назначения лейбла. Результаты реальных тестов проверены в GitHub:

| Тип | Issue | Результат |
|---|---|---|
| feature | [№4 — Поддержка кириллицы](https://github.com/DaniilEF/Homework_7-8_AI/issues/4) | feature |
| bug | [№5 — Строка длиннее 40 символов](https://github.com/DaniilEF/Homework_7-8_AI/issues/5) | bug |
| task | [№6 — Документация тестов](https://github.com/DaniilEF/Homework_7-8_AI/issues/6) | task |
| unknown | [№7 — Нужно что-то улучшить](https://github.com/DaniilEF/Homework_7-8_AI/issues/7) | needs-triage, комментариев нет |

Для расплывчатого Issue в показанном результате классификатора: `type=unknown`, `confidence=0.32`. Это реальный ответ, а не принудительная подстановка для демонстрации. Невалидный ответ или ошибка LLM также безопасно приводят к unknown с confidence=0, но это отдельный случай, не доказательство низкой уверенности модели.

При confidence < 0.8 либо неизвестном типе назначается needs-triage. При ровно 0.8 допустимый известный тип принимается. Основной workflow не публикует комментарии ни в одной ветке; для needs-triage это выполняет требование задания.

Назначение лейбла создаёт ещё одно событие GitHub с action=labeled. Оно может дать короткий Execution до Normalize Issue, но не вызывает классификатор повторно. Это фильтрация событий, не отдельная Data Table дедупликация.

## 2. Еженедельная статистика и Gmail

Расписание: `0 9 * * MON`, timezone workflow — Europe/Moscow, то есть понедельник 09:00 по Москве. Также есть ручной запуск для проверки без ожидания понедельника.

`Report Window` задаёт период в 7 суток. Для расширенного отчёта текущий конец по умолчанию округляется вниз до полного часа, начало — на 7 суток раньше. Интервал имеет вид [start,end); для GitHub конец включительного диапазона уменьшается на секунду. Даты в письме и таблице указаны в UTC.

Четыре HTTP-запроса к `GET https://api.github.com/search/issues`:

1. Все созданные за период Issues: `repo:... is:issue created:START..END`.
2. Та же выборка с `label:bug`.
3. Та же выборка с `label:task`.
4. Та же выборка с `label:feature`.

Ограничение is:issue исключает PR. Это статистика созданных Issues по текущим лейблам, а не числа исправленных ошибок. Закрытый Issue учитывается, если создан внутри периода.

`Group by Type and Author` использует полный набор для итоговых чисел, проверяет согласованность трёх дополнительных выборок и группирует по типам и авторам-создателям. needs-triage и записи без классификации не теряются. Несколько классификационных лейблов выделяются как conflicting-labels, чтобы один Issue не учитывался дважды.

`Build HTML Report` формирует таблицы; пользовательские строки экранируются. Gmail node отправляет HTML-письмо на адрес из Report Settings.

Результат тестового периода: 4 Issues; bug=1, task=1, feature=1, needs-triage=1; автор DaniilEF — 4. ## 3. Data Table, Δ и AI-аннотация

Data Table `weekly_issue_stats` хранит снимки результатов:

| Поле | Тип | Назначение |
|---|---|---|
| repo_full_name | String | Репозиторий |
| period_start | String | Начало периода, ISO UTC |
| period_end | String | Исключённая верхняя граница, ISO UTC |
| total | Number | Число созданных Issues |
| by_type_json | String | JSON со счётчиками типов |
| by_author_json | String | JSON с группировкой по авторам |
| simulated | Boolean | true только для имитированной базы |

`Read Previous Week` читает запись нужного репозитория с period_end, равным началу текущего периода. `Compare Weeks` дополнительно требует точное начало предыдущего периода: на 7 суток раньше. Случайная последняя запись не подменяет прошлую неделю.

Если предыдущей записи нет, previous и delta равны null. Письмо явно сообщает об отсутствии базы; она не считается нулём. Если запись есть, вычисляется current − previous для общего числа, типов и авторов. Учитываются авторы, отсутствующие в одном из периодов.

`Save Weekly Snapshot` выполняет upsert по репозиторию и обеим границам периода. Повтор той же выборки обновляет снимок вместо добавления второй строки. Снимок сохраняется до вызова AI и отправки: сбой почты не удаляет вычисленную статистику.

Для демонстрации использованы:

- тестовая база: 2026-11-03T21:00:00Z — 2026-11-10T21:00:00Z, total=3, bug/task/feature по 1, simulated=true;
- текущие реальные данные: 2026-11-10T21:00:00Z — 2026-11-17T21:00:00Z, total=4, needs-triage=1 дополнительно, simulated=false.

В письме получено Δ total=+1, Δ needs-triage=+1, остальные типы=0; по автору DaniilEF также +1. Имитированная база явно подписана. Одна тестовая неделя разрешена условием.

`Prepare Annotation` передаёт текущую статистику, предыдущую и вычисленную Δ в Basic LLM Chain `AI Weekly Annotation`. Текст выводится блоком «AI-комментарий недели». В показанном письме AI корректно описал +1 и отметил тестовый характер базы. Числа вычисляет Code node; модель их только объясняет.

Подтверждения: [расширенная цепочка](homework/7.2/evidence/05-star-execution.png), [первое письмо без базы](homework/7.2/evidence/06-first-star-email.png), [письмо с Δ и AI-аннотацией](homework/7.2/evidence/07-delta-ai-email.png). [Data Table с двумя периодами и отметкой simulated](homework/7.2/evidence/12-weekly-data-table.png).

## 5. Как воспроизвести

1. Импортировать классификатор, выбрать рабочий LLM credential и опубликовать его.
2. Импортировать Issue Triage, выбрать GitHub credentials и опубликованный классификатор в Call Issue Classifier. В репозитории создать лейблы bug/task/feature/needs-triage и опубликовать workflow.
3. Создать новые Issues всех типов; проверить ответы, ветки и лейблы. Редактирование старого Issue не является новым action=opened.
4. Импортировать расширенный отчёт, выбрать GitHub/Gmail/LLM credentials и одну таблицу weekly_issue_stats в обеих Data Table нодах.
5. Вручную выполнить отчёт; проверить письмо и снимок. Для сравнения использовать реальную прошлую неделю или явно помеченную тестовую запись с точными границами. Зафиксировать обе строки и полученную Δ.
6. После проверки оставить startISO/endISO пустыми и опубликовать расширенный отчёт для расписания. Базовый отчёт не публиковать параллельно.

## 6. Проверки и ограничения

Локальные проверки находятся в homework/7.2/scripts. Они проверяют фильтрацию событий, контракт Sub-workflow, порог 0.8, обработку неизвестного типа, периоды, группировку, экранирование HTML, сравнение снимков и структуру JSON. Локальные тесты не заменяют реальные Executions и полученное письмо.

Четыре запроса возвращают максимум по 100 записей; при усечённом или неполном результате отчёт явно останавливается. Для большего репозитория нужна пагинация. Сравнение недель требует ровно 7 суток и согласованных счётчиков; дубли снимков предыдущей недели вызывают ошибку. Upsert не является общей гарантией против гонок при параллельных запусках. Повтор ручного запуска может повторно отправить письмо.

Credential references в экспортах нужно переназначить при импорте в другой n8n. Секреты в отчёт не включены. При проверке четырёх JSON placeholders и явных токенов по проверенным шаблонам не обнаружено.
