## 1. Установка проверки в GitHub

До запуска autofix в основной ветке main должны находиться `.github/workflows/autofix-contract.yml` и весь каталог `automation/autofix/` с политикой, тестами и фиксированной тестовой фикстурой. Они подготовлены в отдельной локальной ветке `homework-7.2-autofix`. Файлы нужно закоммитить, отправить и включить в main обычным PR; наличие только JSON n8n недостаточно.

В Settings → Actions разрешить GitHub Actions, если они отключены. Workflow использует Node.js 24, не требует npm-пакетов и новых secrets. Токен GitHub Actions имеет только contents:read. Кандидат проверяется на GitHub-hosted runner, без секретов моделей и без токена с правом записи. Исходники тестового скрипта и существующих тестов берутся из base SHA.

Не менять app.js вручную ради демонстрации. Нужен воспроизводимый bug report, относящийся к функции фильтра. Дефект в другой части приложения не входит в разрешённый объём.

## 2. Импорт в n8n

Создать новый workflow → Import from File → выбрать JSON из этой папки. Предыдущие 7.1, классификатор и отчёт не заменяются этим сценарием.

В `Normalize Bug` в начале кода задан config:

```json
{
  "repo": "DaniilEF/Homework_7-8_AI",
  "base": "main",
  "allowedLogins": ["DaniilEF"],
  "fixModel": "openai/gpt-5.2",
  "reviewModel": "openai/gpt-6-sol",
  "maxPolls": 40
}
```

`fixModel` и `reviewModel` фиксируют подписи в данных. При смене модели нужно также поменять ID в соответствующих `Fix Chat Model` и `Review Chat Model`; это две разные модели. Импорт использует те же ID, что уже работали в 7.1. Base — main, поскольку в этом репозитории основная ветка называется main, а не master.

В Bug Events и HTTP Request выбрать рабочие GitHub credentials. Им нужны чтение репозитория/проверок, запись содержимого и PR; для GitHub Trigger — возможность регистрации webhook. В Chat Model выбрать рабочие credentials OpenAI-совместимого провайдера и его Base URL. Новые ключи GitHub Actions не нужны.

После настройки сохранить и Publish. Публикация регистрирует webhook GitHub. В JSON workflow по умолчанию inactive, автоматического запуска от одного импорта нет.

## 3. Запуск по bug report

Принимаются только события своего репозитория от allowedLogins, для открытого Issue с лейблом bug. Поддержаны:

- открытие Issue, уже имеющего bug;
- событие назначения именно лейбла bug (подходит после классификатора 7.2);
- новый комментарий `/fix_bug` в уже открытом bug Issue от разрешённого пользователя.

PR, посторонние репозитории/авторы, обычные комментарии и другие лейблы игнорируются. Сообщения модели обрабатываются как данные, а не команды. Заголовок и описание ограничены 15000 символами.

Описание bug report должно содержать конкретный ввод, фактический результат и ожидаемый результат. Workflow работает с JSON-представимыми строковыми запросами. Не следует использовать старый пример «40 букв и перевод строки» как уже подтверждённый баг: на текущем исходнике при подготовке он не воспроизвёлся. Прежнее предположение о нём оказалось недостаточным.

## 4. Компактная автоматическая цепочка

Схема сокращена с 33 до 24 нод. Проверки не перенесены в другой скрытый workflow: часть подготовительных действий объединена, а несколько чтений GitHub выполняются одним GraphQL-запросом.

| Ноды | Назначение |
|---|---|
| Bug Events → Normalize Bug | Проверка события, автора, bug-лейбла и номера Issue |
| Read Context → Prepare Fix | Одним запросом: base SHA, исходник именно из этого коммита и существующий PR; дубликат прекращает запуск, иначе формируется запрос к AI |
| Generate Fix + Fix Chat Model | Генерация исправления и регрессионных примеров |
| Validate Proposal | Ограничение файлов, сохранение UI, проверка JSON; подготовка атомарного коммита |
| Create Fix Branch → Commit Fix → Verify Commit → Open Fix PR | Отдельная ветка, один коммит с двумя файлами и PR; expectedHeadOid защищает запись от изменения ветки; Verify Commit останавливает создание PR при GraphQL errors даже с HTTP 200 |
| Wait for CI → Read CI → Check CI → CI Ready? | Ожидание проверок; интервал 15 секунд, ограниченное число попыток; после успеха сразу формируется запрос на ревью |
| Review Fix + Review Chat Model | Независимое ревью второй моделью |
| Validate Review → Publish AI Review → Review Approved? | Проверка ответа и публикация ревью; high/critical или approve=false заканчивают цепочку без merge |
| Read Merge State → Guard Merge | Одним запросом: актуальные base/head, состояние PR и проверки; затем применение прежних условий допуска |
| Merge Fix → Confirm Merge | Merge с ожидаемым head SHA и проверка merged=true |

В схеме 22 ноды основного потока и 2 подключённые Chat Model. Инструкционных sticky-note нод и новых sub-workflow нет. При смене базового репозитория конфигурация и credentials должны соответствовать ему.

GitHub Actions должен подтвердить autofix-contract для точного SHA кандидата и принадлежать приложению github-actions. Проверки pending ожидаются, failure/cancelled/timeout останавливают workflow. Серьёзные замечания нельзя обойти противоречивым approve=true: high/critical всё равно запрещают merge.

Ревью публикуется событием COMMENT: это позволяет работать с аккаунтом, который сам создал PR. Допуск к merge вычисляется отдельной политикой, а не формальным GitHub APPROVED от автора собственного PR.

Запросы Read Context и Read Merge State проверены на настоящем GitHub только на чтение. При первом реальном запуске после ручной коррекции branchName удалось создать коммит и PR; autofix-contract отклонил изменение, запретившее допустимые переводы строк. В следующем подтверждённом запуске для Issue №12 цепочка дошла до merge (PR №13). Обычные GraphQL errors в HTTP 200 не считаются успешным результатом политики.

## 5. Что проверяет CI

1. Изменились только app.js и JSON регрессионных примеров этого Issue.
2. Префикс до filterItems и браузерный код после неё сохранены.
3. В функции нет запрещённых механизмов сетевых/системных побочных действий и динамического исполнения.
4. Фиксированный набор прежних правил проходит на кандидате.
5. Хотя бы один сгенерированный пример падает на base, а на кандидате все примеры проходят.
6. Старые тесты из доверенного base проходят на новом app.js.

Проверяемая функция исполняется в ограниченном VM-контексте с таймаутом. VM не объявляется полноценной границей безопасности; основная изоляция — отдельный GitHub-hosted runner без чувствительных secrets и прав записи. Самостоятельно размещённый runner для этого сценария не предусмотрен.

Локальная проверка политики:

```text
node --test automation/autofix/policy.test.cjs automation/autofix/workflow.test.cjs
```

Пятнадцать проверок политики и компактного workflow прошли при подготовке. Внутри одного теста используется явно искусственная неисправная фикстура в памяти. Этот результат не является доказательством реального AI-исправления в n8n и не вносит баг в приложение.

## 6. Если цепочка остановилась

Ошибки модели, неправильный JSON, превышение разрешённых изменений, отсутствие воспроизводимой регрессии, провал/таймаут CI и изменение основной ветки не приводят к merge. После создания PR он остаётся доступен для ручной диагностики. При отклонённом ревью узел Review Approved? заканчивает выполнение по ветке false, без merge; решение видно в опубликованном комментарии.

После неудачной попытки повторный запуск того же Issue не создаёт второй PR. Уже созданная ветка без PR также приведёт к конфликту создания ref вместо перезаписи. Разбор таких попыток выполняется вручную; workflow не удаляет ветки/PR и не force-push-ит.

Base SHA проверяется непосредственно перед merge, а GitHub API блокирует смену head через параметр sha. Это не атомарная блокировка base от сторонних изменений между запросами. Для строгого контроля параллельных merge рекомендуется branch protection с обязательными актуальными проверками; workflow не ослабляет существующие правила защиты.

## Исправления после первого запуска

В актуальном JSON исправлены три ошибки интеграции:

- Готовые GraphQL-запросы формируются в Code-нодах Normalize Bug, Validate Proposal и Validate Review. Read Context, Commit Fix и Read Merge State получают готовый объект через короткое expression со стартовым =. Шаблон с невычисленными {{ ... }} в fixed JSON больше не используется.
- Commit Fix получает `branchName`, а не `refName`, в `CreateCommitOnBranchInput.branch`.
- Verify Commit проверяет GraphQL errors и наличие commit.oid до Open Fix PR. HTTP 200 сам по себе не подтверждает успешный коммит.

Промпт первой модели явно требует сохранить все JS whitespace, включая переводы строк, и не предлагать исправление, если описанный пример уже корректно обрабатывается. Тесты и требования merge не ослаблены. Неподтверждённое описание Issue №5 не заменяет воспроизводимый дефект.

Для обновления импортировать актуальный JSON в новый неопубликованный workflow, выбрать credentials и модели. Перед публикацией снять публикацию со старого autofix-workflow, чтобы один комментарий не запускал две копии. Остальные workflow домашних заданий не затрагиваются. Уже созданные PR и ветки не удаляются и не перезаписываются: повторный /fix_bug для такого Issue не начинает новую попытку.
